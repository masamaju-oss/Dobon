# 真実源（truth/）— 24ドボン デジタル版

このフォルダが、24ドボン デジタル版の唯一の真実源。2026-11-13 に本人が決定し、一本化した。
ここに無いものは「未確定」。作業場（モカの files/）にある生成物は候補であり、正ではない。

## 中身（①〜④）

- ① 再現プロンプト: `prompts/` — 各部品を完全に再現できる仕様・プロンプト
- ② 承認済みカード画像: `approved/` — 本人が承認した成果物だけを置く。承認台帳は `approved/approvals.md`
- ③ 要件: `requirements.md` — ゲームを構成する要件。要件が正であり、コードは道具
- ④ コード: リポジトリ直下のアプリ本体と `tools/`（合成・検品スクリプト）。要件と食い違えばコードを直す／刷新する

数値（座標・角度・中心など）の実行上の正はスクリプト（④）。台帳や要件文書に数値を二重に書かない。

## 状態の定義（3つだけ）

- **候補**: 作業場にある生成物。真実源の外。
- **検品済み**: 検品スクリプトの基準を通ったもの。まだ真実源の外。
- **承認済み**: 本人が承認し、このフォルダに登録されたものだけが「正」。実装はここからしか取り出さない。

要件1件ごとの状態は `requirements.md` 内のタグで管理する:
本人が決定した ／ 未決・モカの提案 ／ 決定済みだが実装に既知の欠陥がある、または前提が変わった。

## データを渡して保管する流れ（日常）

1. モカが候補を作り、検品を通してから、チャットで画像を提示する
2. 本人は OK / NG を言うだけ
3. OK ならモカが真実源へ登録する: 画像・対応する要件番号・再現プロンプトを1回のコミットで入れ、承認台帳に「何を・いつ・どの要件で承認したか」を記録する
4. NG なら候補は作業場で止まる。理由は `requirements.md` の「未解決の問題」に残す
5. 登録したら、モカはコミットへのリンク付きで報告する

## 変更の手順

1. 要件を変えるときは、先に `requirements.md` を直してコミットする（変更理由をコミットメッセージに書く）
2. その後、①プロンプト・②画像・④コードを追従させる
3. 古い承認画像は `approved/` から外す（履歴には残る）

## 移行について（2026-11-13）

- 現在の画像各種は本人の判定で「まだ本番に耐えられない」ため、承認済みとしては登録しない。`approved/` は空から始める。
- 既存の蓄積（iron-plate-spec 等）は `prompts/` に移行ドラフトとしてコピー済み（状態: 提案中）。
- 過去に承認の記録がある単体アセット（紋章 v4、ボスの信頼コイン等）は `approved/approvals.md` に「承認の記録あり・再確認待ち」として記載し、再確認が済むまで `approved/` には入れない。
